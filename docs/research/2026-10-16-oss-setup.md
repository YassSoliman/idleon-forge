# Open-source repo setup for humans and AI agents (2026-10-16)

Ticket: [#7](https://github.com/YassSoliman/idleon-forge/issues/7), part of map [#1](https://github.com/YassSoliman/idleon-forge/issues/1).

Question: what should a small, public, GPL-3.0 monorepo ship so that people, and their AI coding agents, can onboard and contribute quickly while the owner keeps the final say?

This is a recommendation only. None of the files below exist on `main` yet; a later task builds them.

## Answer

- **One agent file, two names.** Write the agent instructions once in a root `AGENTS.md` (the cross-tool open format, now stewarded by the Agentic AI Foundation under the Linux Foundation). Add a one-line `CLAUDE.md` containing `@AGENTS.md`. Claude Code v2.1.277+ reads `AGENTS.md` natively, but only when no `CLAUDE.md` exists, and the import also covers older or restricted sessions without loading the file twice. Keep it under 200 lines, put commands first, and point to `GLOSSARY.md`, `docs/adr/` and ADR 0004 rather than repeating them. Add a per-package `AGENTS.md` only where a package's rules differ (the nearest file wins).
- **The minimal file set** (11 files): `README.md` (already exists, gets a "Contribute" section), `CONTRIBUTING.md`, `AGENTS.md`, `CLAUDE.md`, `CODE_OF_CONDUCT.md` (Contributor Covenant 3.0), `SECURITY.md`, `.github/CODEOWNERS`, `.github/PULL_REQUEST_TEMPLATE.md`, and `.github/ISSUE_TEMPLATE/` holding `config.yml` plus three issue forms (`bug.yml`, `kb-correction.yml`, `idea.yml`). Also add `docs/agents/triage-labels.md`. Skip SUPPORT, FUNDING, GOVERNANCE and a CLA for now.
- **CONTRIBUTING has two equal tracks: code and Knowledge Base.** A Knowledge Base contribution is a PR (or a `kb-correction` issue) that changes one entry and must carry its Source URL, the patch it was verified on, and its tier under ADR 0004. "Patch changed X" reports are first-class contributions, not bugs.
- **Owner keeps the final say with what is already half-configured.** Classic branch protection on `main` already requires 1 approval plus code-owner review, blocks force pushes and deletions, and leaves admins un-enforced, but there is no CODEOWNERS file yet, so the code-owner rule does nothing. Add `* @YassSoliman` to CODEOWNERS. Then every outside PR needs Yasser's approval, and Yasser merges his own PRs through admin bypass. Add Joseph as a collaborator (write). Optionally co-own the Knowledge Base path (`/packages/knowledge-base/ @YassSoliman @JoKhalil`) so either of you can approve Knowledge Base PRs.
- **Owner-only deploy path:** merge to `main` is the only trigger. Deploy from a GitHub Actions job bound to a `production` environment that only `main` may deploy to, with the Cloudflare token stored as an environment secret. Fork PRs never receive secrets. Either add Yasser as a required reviewer, or rely on the merge gate alone. Do not also connect Cloudflare Workers Builds to the same Worker, because that would create a second deploy path the GitHub gates don't cover.
- **Labels:** keep the GitHub defaults and the `wayfinder:*` labels. Add the five triage roles (`needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`, the last of which already exists) plus area labels `area:kb`, `area:parser`, `area:activeon`, and one `patch-stale` label for Knowledge Base entries that a game patch has overtaken.
- **Security:** a short `SECURITY.md` that routes reports through GitHub private vulnerability reporting (enable it in Settings). It should name the real risk surface: the Firebase/OAuth login, tokens that stay in the browser, and save data that must never be committed.
- **Crediting IdleOn Toolbox under GPL-3.0:** keep the full licence text. Vendor the fork under one package with an `UPSTREAM.md` giving Morta1's repo URL, the pinned commit SHA and the re-sync date. Mark modified files with a dated "Modified by IdleOn Forge" note (GPL-3.0 §5a). Use `SPDX-License-Identifier: GPL-3.0-only`, **not** "or later", because Toolbox is GPL-3.0-only. Keep the README credit.
- **DCO / CLA: neither is worth it yet.** On GitHub, inbound=outbound is already the default under the Terms of Service. A CLA mainly enables relicensing, which the GPL-3.0-only Toolbox code rules out anyway. Instead, put a lightweight AI-assistance rule in CONTRIBUTING (disclose the tool, a human fully understands and answers for every line, no AI-generated media). Revisit the DCO only if outside contributors start arriving in volume.

## Details

### 1. `AGENTS.md` and `CLAUDE.md`: current conventions (as of 2026-10-16)

**AGENTS.md** is "a dedicated, predictable place to provide the context and instructions to help AI coding agents work on your project", "stewarded by the Agentic AI Foundation under the Linux Foundation". It is read by Codex, Jules, Aider, GitHub Copilot, VS Code, Cursor, Zed, Warp and others. In monorepos, "agents automatically read the nearest file in the directory tree, so the closest one takes precedence" ([agents.md](https://agents.md/), fetched 2026-10-16). Suggested sections: project overview, build and test commands, code style, testing, security, commit/PR guidelines, deployment.

**Claude Code** ([memory docs](https://code.claude.com/docs/en/memory), fetched 2026-10-16):
- Project instructions live at `./CLAUDE.md` or `./.claude/CLAUDE.md`. Personal ones live in `./CLAUDE.local.md`, which should be gitignored.
- Claude Code reads `AGENTS.md` directly (v2.1.277+), **but only when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md`** in the working directory or above it. If one of those exists, it reads "Your `CLAUDE.md` files only". That means a contributor who adds a personal `CLAUDE.local.md` silently stops getting `AGENTS.md`.
- The documented sharing pattern is a `CLAUDE.md` containing `@AGENTS.md`, with any Claude-specific notes below the import: "Keeping the import never makes Claude read `AGENTS.md` twice". The docs also allow a symlink, but on some platforms (Windows checkouts) a symlink is less robust than a one-line import file. **Recommendation: use the import.**
- Size: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." Imports don't reduce that cost. Move path-specific rules into `.claude/rules/*.md` with `paths:` frontmatter, which load only when Claude touches matching files.
- Instructions are context, not enforcement. "To block an action regardless of what Claude decides, use a PreToolUse hook." For example, "never commit raw saves" is enforced by `.gitignore` (already present) plus CI, not by prose.

**GitHub Copilot** reads `.github/copilot-instructions.md`, path-scoped `.github/instructions/*.instructions.md`, and `AGENTS.md` / `CLAUDE.md` / `GEMINI.md` "used by AI agents" ([GitHub Docs](https://docs.github.com/en/copilot/how-tos/configure-custom-instructions/add-repository-instructions), fetched 2026-10-16). With `AGENTS.md` in place, no separate Copilot file is needed.

**Examples from well-run projects:**
- `astral-sh/uv` [AGENTS.md](https://github.com/astral-sh/uv/blob/main/AGENTS.md) (last changed 2026-10-08): a terse list of ALWAYS/NEVER/PREFER rules that defers to CONTRIBUTING for tooling. This is a good model for the length and tone.
- `ghostty-org/ghostty` [AGENTS.md](https://github.com/ghostty-org/ghostty/blob/main/AGENTS.md) (2026-04-08): commands first, directory map, and "Issue and PR Guidelines: Never create an issue. Never create a PR." This shows that agent instructions can bound what agents do on the tracker, not just how they write code.
- `Morta1/IdleonToolbox` ships its own `CLAUDE.md` (seen in the repo root, 2026-10-16). It is upstream prior art for the parser package.

**Recommended `AGENTS.md` outline for the Forge** (about 60–120 lines):
1. What this is (2 lines) plus links: `GLOSSARY.md` ("use these terms"), `docs/adr/`, `docs/agents/issue-tracker.md`.
2. Commands: install, build, test, lint, typecheck, run ActiveOn locally (filled in once the stack is chosen).
3. Repo map: `apps/activeon`, `packages/toolbox-parsers` (vendored fork: do not refactor; see `UPSTREAM.md`), `packages/knowledge-base`, `packages/account-state`.
4. Hard rules: read-only toward the game; no LLM at advice time (ADR 0002); every Knowledge Base entry has a Source plus patch (ADR 0004); never commit saves, tokens or `fixtures/private/`; GPL-3.0-only headers.
5. Knowledge Base research procedure: newest source first, record date and patch, flag stale material.
6. PR rules: one concern per PR, run tests, fill in the template, disclose AI use, no AI attribution footers in commits, never push to `main`.

### 2. README structure

The README already has a pitch, status, principles, "Read first", credits and licence. Add:
- **Quick start**: clone, install, run (once code exists).
- **Contribute**: two lines linking CONTRIBUTING ("fix code" or "fix a fact in the Knowledge Base") plus `good first issue`.
- **For AI agents**: one line, "agents: start at `AGENTS.md`".
- **Disclaimer**: keep "Not affiliated with LavaFlame2" and add "never asks for or stores your password server-side" once the auth design is settled.

### 3. CONTRIBUTING

Model it on uv's and Ghostty's (Ghostty: discuss first, "all issues are actionable" ([CONTRIBUTING](https://github.com/ghostty-org/ghostty/blob/main/CONTRIBUTING.md))):
- **Before you start:** open or claim an issue. Large changes start as an issue.
- **Code track:** setup, tests, branch naming, PR template, review by the owner.
- **Knowledge Base track:** the entry schema, the required fields (Source URL, source tier per ADR 0004, verified-on patch and date), how to mark an entry `patch-stale`, and how to file a `kb-correction` issue without writing code. This is the low-barrier path for players who aren't developers.
- **AI-assisted contributions:** this is now a common convention. A study of 1,000 popular repos found 118 AI policies, 51% requiring disclosure and 74% a human in the loop ([arXiv 2605.16706](https://arxiv.org/abs/2605.16706), May 2026, secondary summary). The primary models are:
  - Ghostty's [AI_POLICY.md](https://github.com/ghostty-org/ghostty/blob/main/AI_POLICY.md) (2026-02-15): "All AI usage in any form must be disclosed"; "The human-in-the-loop must fully understand all code"; "No AI-generated media"; maintainers exempt.
  - The Linux kernel's [coding-assistants guide](https://docs.kernel.org/process/coding-assistants.html): "AI agents MUST NOT add Signed-off-by tags", plus an `Assisted-by:` trailer.

  For the Forge, use a short section in CONTRIBUTING (not a separate file): disclose the tool in the PR body, a human answers for every line, and there is no AI attribution in commits. That last rule matches the owner's standing rule for public repos. Since the project's own Knowledge Base is AI-researched (ADR 0002), the rule should be about accountability and citations, not anti-AI.

### 4. Issue and PR templates

Issue forms are YAML in `.github/ISSUE_TEMPLATE/` (still labelled "public preview") and support inputs, dropdowns, checkboxes and required validation ([GitHub Docs](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/configuring-issue-templates-for-your-repository)). uv's set (`1_bug_report.yaml`, `2_feature_request.yaml`, `3_question.yaml`, plus `config.yml` with contact links) is a compact model ([uv/.github/ISSUE_TEMPLATE](https://github.com/astral-sh/uv/tree/main/.github/ISSUE_TEMPLATE)).

For the Forge:
- `bug.yml`: what you saw, what you expected, browser, world/stage. Plus a required checkbox: "I did not paste my save, tokens or login".
- `kb-correction.yml`: the entry/topic, what's wrong, a Source URL (required), the patch/date of the source, and a dropdown for the ADR 0004 tier (game data / wiki edited after the patch / dated guide / other). Labels: `area:kb`, `needs-triage`.
- `idea.yml`: the problem, not the solution. Label: `needs-triage`.
- `config.yml`: `blank_issues_enabled: false` (Wayfinder tickets are created through `gh`, which bypasses forms anyway), plus a contact link to `SECURITY.md`.
- `PULL_REQUEST_TEMPLATE.md`: copy uv's minimal **Summary / Test Plan** ([template](https://github.com/astral-sh/uv/blob/main/.github/PULL_REQUEST_TEMPLATE.md)) and add **Sources** (for Knowledge Base changes) and **AI assistance** (tool used, or "none").

### 5. CODEOWNERS, branch protection and the owner-only deploy path

Facts ([About code owners](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners)):
- The file lives in `.github/`, root or `docs/` (first found wins).
- Owners need explicit write access.
- "The last matching pattern takes the most precedence."
- Approval from *any* listed owner satisfies code-owner review.
- Protect the CODEOWNERS file itself by giving it an owner.

**Current state of `main`** (read via `gh api repos/YassSoliman/idleon-forge/branches/main/protection`, 2026-10-16):

| Setting | Value |
|---|---|
| `required_approving_review_count` | 1 |
| `require_code_owner_reviews` | true |
| `dismiss_stale_reviews` | false |
| `require_last_push_approval` | false |
| `enforce_admins` | false |
| `allow_force_pushes` / `allow_deletions` | false |

There are no rulesets. The only collaborator is YassSoliman (admin), so **Joseph is not yet a collaborator**. There is no CODEOWNERS file, so the code-owner requirement currently has no effect.

By default, branch protection "don't apply to people with admin permissions", and that is optional to change ([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). So with `enforce_admins: false`, Yasser can merge his own PRs, and everyone else needs his approval: exactly "one approval, owner has the final say".

Recommended `.github/CODEOWNERS`:
```
*                          @YassSoliman
/packages/knowledge-base/  @YassSoliman @JoKhalil
/.github/                  @YassSoliman
```
The Knowledge Base co-ownership is optional. It lets Joseph approve Knowledge Base PRs, including Yasser's, without Yasser using bypass.

Also turn on **Dismiss stale pull request approvals when new commits are pushed** ([available rules](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)), so approval can't be gamed by pushing after review. Add **Require status checks** once CI exists. Leave "require approval of the most recent reviewable push" off: with two people it would block the owner's own fix-ups.

Rulesets are an alternative. Their bypass list supports **"For pull requests only"**, which forces even the owner through a PR while still letting him merge it ([Creating rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)). *Flag:* the [About rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets) page words availability as "GitHub Team and GitHub Enterprise plans", but the rulesets API answered 200 `[]` on this Free personal public repo. Verify in Settings before relying on it. Classic protection is already working, so it is the safe default.

**Deploy path.** GitHub Free supports environments and "Deployment protection rules for public repositories" ([GitHub's plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans); [Managing environments](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)):
- Required reviewers: up to 6, and one is enough.
- Optional **Prevent self-review**.
- Deployment branches restricted to `main`.
- Environment secrets "only available to workflow jobs that use the environment ... after any configured rules ... pass".
- Uncheck "Allow administrators to bypass".

Separately, "secrets are not passed to the runner when a workflow is triggered from a forked repository", and `GITHUB_TOKEN` is read-only there ([Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

Recommended pipeline:
1. A `deploy.yml` on `push` to `main`, with `environment: production`.
2. `CLOUDFLARE_API_TOKEN` stored only as a `production` environment secret.
3. Deployment branches: `main` only.

With only `main` able to deploy and only owner-approved PRs reaching `main`, Yasser owns deploys. Adding Yasser as a required reviewer on the environment adds a second click per deploy. Skip that, given the map wants "every merge to `main` deploys".

Cloudflare Workers Builds (Git integration) deploys the production branch and builds previews for other branches ([Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/)). Its docs don't say how it handles fork PRs. Pick **one** deploy mechanism. If Workers Builds is preferred for preview URLs, it is still gated by the same `main` protection, but GitHub environments no longer guard the token.

### 6. Labels

The repo today has the 10 GitHub defaults (bug, documentation, duplicate, enhancement, good first issue, help wanted, invalid, question, wontfix, accessibility) plus `wayfinder:{map,research,grilling,prototype,task}` (`gh label list`, 2026-10-16).

Add:
- the triage roles `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human` (`wontfix` already exists);
- `area:kb`, `area:parser`, `area:activeon`;
- `patch-stale`.

Record the meanings in `docs/agents/triage-labels.md`, next to the existing `issue-tracker.md`, so triage tooling and agents read one source. `ready-for-agent` is useful precisely because contributors' agents can pick those issues up from the frontier.

### 7. Code of conduct

Use Contributor Covenant **3.0** ([contributor-covenant.org/version/3/0](https://www.contributor-covenant.org/version/3/0/), page copyright 2026). It supersedes 2.1. Adoption means copying the text and filling in the reporting contact ("[INSERT CONTACT METHOD]"). For a two-person project, name a single email and say the owner enforces it.

### 8. Security policy

`SECURITY.md` is a recognised community health file, valid in `.github/`, root or `docs/` ([community health files](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file)). Enable **private vulnerability reporting** (Settings → Advanced Security), which adds a "Report a vulnerability" button on the Advisories page ([GitHub Docs](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configuring-private-vulnerability-reporting-for-a-repository)). `openai/codex` and `astral-sh/uv` both ship a root `SECURITY.md`.

Content:
- **Supported:** `main` / the live URL only.
- **How to report:** the advisory button, never a public issue.
- **In scope:** auth flows, token handling, anything that could write to a game account, leaked save data.
- **Out of scope:** the game's own servers.
- **Response:** best effort, no SLA.

Given the [ecosystem findings](2026-10-16-ecosystem.md) (every tool reuses Lava's OAuth clients, and Toolbox ships a Google client secret), the policy should also say how the project responds if upstream credentials rotate.

### 9. Crediting IdleOn Toolbox under GPL-3.0

Facts:
- Toolbox's `package.json` says `"license": "GPL-3.0-only"`, and GitHub detects GPL-3.0. Its source files carry **no per-file copyright headers** (checked `parsers/index.ts` and `LICENSE` via `gh api`, upstream HEAD `f1e4240`, 2026-10-16T20:40Z).
- GPL-3.0 §4 requires you to "keep intact all notices stating that this License ... appl[ies]".
- §5(a) requires: "The work must carry prominent notices stating that you modified it, and giving a relevant date" ([GPL-3.0 text](https://www.gnu.org/licenses/gpl-3.0.txt)).

Recommendation:
1. Keep root `LICENSE` (already GPL-3.0 text) and the README credit line.
2. In `packages/toolbox-parsers/`, add:
   - `UPSTREAM.md`: the upstream URL, author (Morta1), licence (GPL-3.0-only), pinned commit SHA plus date, the re-sync procedure from ADR 0001, and a dated changelog of local modifications. That changelog is the §5(a) "prominent notice".
   - A short header on each file we modify:
     `// Derived from IdleOn Toolbox (https://github.com/Morta1/IdleonToolbox) by Morta1, GPL-3.0-only. Modified by IdleOn Forge contributors, <date>.`
3. Declare licensing with SPDX identifiers (`SPDX-License-Identifier: GPL-3.0-only`). This follows the REUSE 3.3 convention (2024-11-14) of `SPDX-FileCopyrightText` plus `SPDX-License-Identifier` headers, or a `REUSE.toml` for bulk paths ([REUSE spec 3.3](https://reuse.software/spec-3.3/)). Full REUSE compliance is optional. A `REUSE.toml` that covers the vendored folder in one stanza is the cheapest way to make provenance machine-readable.
4. **Use `GPL-3.0-only`, not the FSF template's "or (at your option) any later version".** We cannot grant "or later" on code that we received as "only". Set `"license": "GPL-3.0-only"` in every `package.json` and use that identifier in `AGENTS.md`, so agents don't generate "or-later" headers.

### 10. DCO or CLA?

- **CLA: no.** [opensource.guide/legal](https://opensource.guide/legal/) (last changed 2026-02-10) says: "For the vast majority of open source projects, an open source license implicitly serves as both the inbound ... and outbound ... license. If your project is on GitHub, the GitHub Terms of Service make 'inbound=outbound' the explicit default". A CLA adds admin work, and Node.js dropped theirs to lower the barrier to entry. The usual reason for a CLA is the right to relicense, and that doesn't apply here: the Toolbox-derived core is GPL-3.0-only, which we can't relicense regardless.
- **DCO: not yet.** The DCO 1.1 ([developercertificate.org](https://developercertificate.org/)) is cheap: a `Signed-off-by:` trailer via `git commit -s`. GitHub's built-in "require signoff" only applies to web-interface commits; for CLI commits, authors must use `--signoff` ([GitHub Docs](https://docs.github.com/en/organizations/managing-organization-settings/managing-the-commit-signoff-policy-for-your-organization)). Enforcing it on CLI commits needs a check app, which adds friction for players fixing one Knowledge Base fact. If added later, follow the kernel rule that AI agents must not add `Signed-off-by` ([kernel docs](https://docs.kernel.org/process/coding-assistants.html)).
- **Trigger to revisit:** regular contributors beyond Yasser and Joseph, or any contribution of copied third-party content into the Knowledge Base (for example, pasted guide text).

## Flags and caveats

- **Rulesets on a Free personal repo:** the GitHub docs wording conflicts with the API's behaviour (section 5). Verify before choosing rulesets over classic protection.
- **Claude Code's AGENTS.md behaviour is new** (v2.1.277+, with Bedrock and no-telemetry sessions only from v2.1.281). The `@AGENTS.md` import in `CLAUDE.md` makes the setup independent of the version.
- **Issue forms are still "public preview"** on GitHub.
- **Joseph has no repo access yet,** so the one-approval flow and Knowledge Base co-ownership do nothing until he is added as a collaborator.
- **The local `.claude/settings.local.json` is untracked** but not listed in the repo `.gitignore`. Add `.claude/settings.local.json` and `CLAUDE.local.md` so contributors don't commit personal agent config.
