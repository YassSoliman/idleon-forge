# Cloudflare hosting shape for the Forge: research for ActiveOn (2026-10-16)

Ticket: [#6](https://github.com/YassSoliman/idleon-forge/issues/6), part of map [#1](https://github.com/YassSoliman/idleon-forge/issues/1).
Question: what Cloudflare setup should the Forge monorepo use, given Yasser's existing account on Workers Paid ($5/mo)?

Method: I read the current Cloudflare docs (developers.cloudflare.com, using each page's `index.md` view and recording its "Last updated" date), the `cloudflare/wrangler-action` README and releases, and the GitHub Actions docs. I also sent unauthenticated CORS preflight (`OPTIONS`) probes to the login endpoints that the ecosystem research identified. I did not touch any Cloudflare account. Confidence: **H** = stated in a primary doc, **M** = inferred from primary docs, **L** = not documented anywhere.

Recency warning: **Worker Previews** (`wrangler preview`) is new. Its pages were last updated 2026-09-22 to 2026-10-01, and it needs Wrangler ≥ 4.135.0 (docs) or ≥ 4.136.3 (wrangler-action README). On 2026-10-16 the latest Wrangler on npm was 4.151.1. Older guides and AI answers will tell you to use Pages preview deployments or `wrangler versions upload --preview-alias`. **Both are now the old way.**

## Answer

- **Use Workers with static assets, not Pages.** Pages' own landing page now says: "[Workers] is Cloudflare's primary platform for building applications. Start new projects with Workers." Every Pages feature ActiveOn needs (preview URLs, custom domains, `_headers`/`_redirects`) has a Workers equivalent. (H)
- **The MVP needs an assets-only Worker and nothing else: no Worker script, KV, D1 or Durable Objects.** The config is just `assets.directory` plus `not_found_handling = "single-page-application"`. Requests to static assets are "free and unlimited", so the $5 plan's request and CPU quotas never come into play. Account State stays in the browser. The login endpoints the game uses (Google device-code/token, Lava's Steam `asil` cloud function) answer a CORS preflight from an arbitrary `*.workers.dev` origin with that origin echoed back, so the browser can call them directly and no proxy Worker is needed. (H for the docs, M for the CORS result: preflight only, not a full sign-in)
- **CI: GitHub Actions running `wrangler deploy` on push to `main`, and `wrangler preview --name pr-<N>` on each PR, deleted when the PR closes.** Cloudflare publishes this exact workflow. Actions minutes are free in public repos. The alternative, Workers Builds (Cloudflare's own Git CI), also comments preview URLs on PRs, but it keeps build config in the dashboard where contributors can't see it, and nothing documents it building PRs from forks. (H)
- **Use Previews, not Version URLs.** Cloudflare's docs say: "Do not use Version URLs for branch or pull request testing. Use Previews instead." A Preview URL looks like `pr-12-<worker>.<subdomain>.workers.dev`. It always serves the branch's latest deploy and carries `X-Robots-Tag: noindex`. (H)
- **Domain: launch on `*.workers.dev`, add a Custom Domain once the branding ticket picks a name.** A Custom Domain needs a zone on Cloudflare, and Cloudflare creates the DNS record and certificate itself. One catch: changing the origin later empties each user's localStorage/IndexedDB (saved login, settings), so pick the domain before the app holds much state. (H, M for the origin catch)
- **How Joseph and outside contributors get previews without Cloudflare access:** the PR comment carries the URL, and Previews are public by default. If Joseph has write access to the repo, he pushes branches there and his PRs get previews automatically. **PRs from forks get no secrets** (that is GitHub's rule), so their previews need a maintainer-gated step (see §5). Never use `pull_request_target` with a checkout of the PR's code. (H)
- **Secrets:** exactly two, both in GitHub: `CLOUDFLARE_API_TOKEN`, a custom token limited to Edit Workers Scripts on the one account, and `CLOUDFLARE_ACCOUNT_ID`. Put the production deploy job in a GitHub `production` environment that only `main` may deploy to. The game's Firebase web config is public by nature, so it is not a secret. The app has no runtime secrets in the MVP. (H)
- **Limits we would hit first:** none are close. The ones to know: 500 Previews per Worker (the oldest is auto-deleted), 100 deployments per Preview, 100,000 files per version, 25 MiB per file (watch any single bundled Knowledge Base or game-data JSON), 100 `_headers` rules, and a 63-character DNS label for `<preview>-<worker>`. The Free-plan Worker limits (10 ms CPU, 100k requests/day) only matter if we later add a Worker script. (H)

Suggested `apps/activeon/wrangler.jsonc` (illustrative; the Worker name is up to the domain/branding ticket):

```jsonc
{
  "name": "activeon",
  "compatibility_date": "2026-10-16",
  "assets": { "directory": "./dist", "not_found_handling": "single-page-application" },
  "workers_dev": true,
  "preview_urls": true,
  "previews": {}

```

`assets` must stay at the top level. `wrangler preview` uploads the assets from the branch being previewed ([Previews configuration](https://developers.cloudflare.com/workers/previews/configuration/), 2026-09-22). `preview_urls` turns on `workers.dev` Preview URLs ([Previews custom domains](https://developers.cloudflare.com/workers/previews/custom-domains/), 2026-09-24).

## 2. Deploy on merge, and a preview per PR

**Previews are now the official mechanism.** "Previews are the recommended way to test changes before production." Each Preview is an isolated copy under the same Worker, with its own vars, secrets and bindings, and it does **not** inherit production settings. Version URLs "use production resources", and the docs say not to use them for PRs. To migrate from `wrangler versions upload --preview-alias X`, run `npx wrangler preview --name X` instead. (H, [Previews](https://developers.cloudflare.com/workers/previews/) 2026-09-24; [Compare workflows](https://developers.cloudflare.com/workers/previews/compare-workflows/) 2026-09-22)

Each Preview has two kinds of URL:

- the **Preview URL** `<preview-name>-<worker-name>.<subdomain>.workers.dev`, which always serves the latest deploy;
- a **Deployment URL** `<deployment-id>-<worker-name>.<subdomain>.workers.dev`, which is immutable. (H, [Previews](https://developers.cloudflare.com/workers/previews/))

Cloudflare's GitHub Actions example ([Previews examples](https://developers.cloudflare.com/workers/previews/examples/), 2026-10-01) does the following:

- triggers on `pull_request` with types `[opened, synchronize, reopened, closed]`, with `permissions: contents: read, pull-requests: write`;
- runs `npx wrangler preview --name "pr-${{ github.event.pull_request.number }}" --json`, reads `.preview.urls[0]` with `jq` and posts it with `gh pr comment` (add `--edit-last --create-if-none` to keep a single comment);
- has a cleanup job on `closed` that runs `npx wrangler preview delete --name "pr-<N>" --skip-confirmation`;
- shows optional extras: a probe step and a Playwright screenshot uploaded as an artifact.

You can use `cloudflare/wrangler-action@v4` (latest v4.1.3, 2026-09-24) in place of raw `npx`. Its README gives `command: preview --name pr-<N>` and `gitHubToken` (needs `deployments: write`). The action exposes the outputs `preview-url`, `preview-deployment-url` and `preview-name`, and creates a GitHub Deployment. The README pins **Wrangler 4.136.3+**, while the Cloudflare docs say 4.135.0+. Pin the newer one. (H, [wrangler-action README](https://github.com/cloudflare/wrangler-action))

Production runs `wrangler deploy` on `push` to `main`, using the same action and secrets. (H, [GitHub Actions for Workers](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/), 2026-09-18)

**Monorepo:** Preview names are scoped to a Worker, so each Mod's Worker can have its own `pr-123` Preview ([Previews examples](https://developers.cloudflare.com/workers/previews/examples/#monorepo-with-multiple-workers)). In Actions, use a path filter or a per-app job so that one Mod's PR doesn't redeploy every app. (M)

**Workers Builds instead of Actions:**

- Workers Builds connects the repo in the dashboard and runs a production build on pushes to the production branch, plus "preview builds" on other branches. New Workers default to `npx wrangler preview`.
- On GitHub it comments the Preview URL on the PR and posts per-Worker check runs.
- For monorepos it supports a root directory and build watch paths per Worker.
- Paid limits: 6,000 build minutes/month, 6 concurrent builds, 20-minute timeout.
- Its API token is auto-generated, so GitHub holds no secret.
- **Builds run on pushes to the connected repo's branches. Nothing documents fork PRs.** Pages, the closest sibling, says outright that "preview URLs will not be created for pull requests created from forks". Assume Builds behaves the same. (H for the features, L for the fork behaviour.)

Sources: [Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) (2026-10-15), [Build branches](https://developers.cloudflare.com/workers/ci-cd/builds/build-branches/) (2026-10-01), [GitHub integration](https://developers.cloudflare.com/workers/ci-cd/builds/git-integration/github-integration/) (2026-10-15), [Advanced setups](https://developers.cloudflare.com/workers/ci-cd/builds/advanced-setups/) (2026-09-22), [Builds limits](https://developers.cloudflare.com/workers/ci-cd/builds/limits-and-pricing/) (2026-05-29), [Pages GitHub integration](https://developers.cloudflare.com/pages/configuration/git-integration/github-integration/).

Verdict: Builds is a valid fallback, but Actions fits better. ADR 0003 makes contributor onboarding part of the product, and with Actions the pipeline lives in the repo where contributors can read it and propose changes. Actions is also the only path where we control fork-PR handling. "GitHub Actions usage is free … for public repositories that use standard GitHub-hosted runners." (H, [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions))

## 3. What needs a Worker, KV, D1 or Durable Objects in the MVP

- **Nothing.** The ecosystem research shows the existing tools are static sites that talk to the game's Firebase project (`idlemmo`) straight from the browser. Toolbox is a Next.js static export. Its one Worker is the Apple-login proxy, and the MVP doesn't need Apple: Yasser uses Google and Joseph uses Steam. ([ecosystem research](./2026-10-16-ecosystem.md) §1)
- **CORS probe (2026-10-16):** I sent `OPTIONS` with `Origin: https://idleon-forge.example.workers.dev` to three endpoints:
  - `https://us-central1-idlemmo.cloudfunctions.net/asil` (Steam) returned `204` with `access-control-allow-origin` set to our origin and `allow-methods: POST`;
  - `https://oauth2.googleapis.com/device/code` returned `200` with our origin echoed;
  - `https://oauth2.googleapis.com/token` returned `200` with our origin echoed.

  These endpoints echo any origin, so a browser on `workers.dev` or a custom domain can call them directly. **I only sent preflights, not a full sign-in.** Firebase API-key referrer restrictions and Firestore reads are left to the auth ticket. (M)
- **Keep advice deterministic and in the browser ([ADR 0002](../adr/0002-deterministic-advice-ai-built-knowledge.md)).** The Knowledge Base ships as a static asset with the build.
- **What would first need a Worker script (all out of MVP scope):** the background push server (needs a server-held token, and the map rules it out), an Apple-login proxy, public profile sharing, and server-side save polling in the style of ha-idleon. If one gets added:
  - Previews auto-isolate Durable Objects, but each KV/D1/R2 binding needs a separate Preview-safe resource ([Previews resources](https://developers.cloudflare.com/workers/previews/resources/), 2026-09-22).
  - Cron Triggers, Queue consumers and routes always target production.
  - Service bindings from a Preview hit the production target.

## 4. Custom domain vs `*.workers.dev`

| Option | Finding | Conf | Source |
|---|---|---|---|
| `workers.dev` | Production is `<worker>.<subdomain>.workers.dev`. Preview URLs get `X-Robots-Tag: noindex` automatically. Needs no DNS. | H | [Previews](https://developers.cloudflare.com/workers/previews/), [Previews custom domains](https://developers.cloudflare.com/workers/previews/custom-domains/) |
| Custom Domain | Needs "an active Cloudflare zone". Cloudflare creates the DNS records and certificates. Fails on a hostname that already has a CNAME. Set it in Wrangler with `routes: [{ pattern, custom_domain: true }]`. | H | [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) (2026-09-29) |
| Previews on a custom domain | Optional: `previews_enabled: true` on the route gives `<preview>.app.example.com`. Cloudflare creates a wildcard DNS record and certificate, so use a dedicated hostname to avoid wildcard conflicts. `noindex` is **not** added automatically here (add it via `_headers`). | H | [Previews custom domains](https://developers.cloudflare.com/workers/previews/custom-domains/) |
| Pages comparison | `*.pages.dev` plus up to 100 custom domains per project on Free. Irrelevant now that Pages is not recommended. | H | [Pages limits](https://developers.cloudflare.com/pages/platform/limits/) (2026-09-05) |

Recommendation: ship the MVP on `workers.dev` and keep Previews on `workers.dev` for good (free `noindex`, no wildcard certificate). Add one production Custom Domain when the domain/branding open item (map #1, "Not yet specified") is decided. Since a new origin starts with empty browser storage, do the switch early, or plan a one-time re-login. (M)

## 5. Previews for Joseph and outside contributors, without Cloudflare access

- **Nobody but Yasser needs a Cloudflare login.** The workflow posts the Preview URL on the PR, and "Preview URLs are public by default". (H, [Previews](https://developers.cloudflare.com/workers/previews/))
- **Joseph (collaborator):** if he has write access and pushes branches to `YassSoliman/idleon-forge`, the `pull_request` workflow has the repo secrets and previews just work. (H, [GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows))
- **Fork PRs:** "With the exception of `GITHUB_TOKEN`, secrets are not passed to the runner when a workflow is triggered from a forked repository", and `GITHUB_TOKEN` is read-only there. First-time contributors may need maintainer approval before workflows run at all. Cloudflare's own example says to guard the secret-using steps with `github.event.pull_request.head.repo.full_name == github.repository`, so fork PRs get no preview. (H, [GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [Previews examples](https://developers.cloudflare.com/workers/previews/examples/))
- **Giving fork PRs a preview later** (optional, maintainer-gated):
  1. The `pull_request` workflow builds `dist/` with no secrets and uploads it as an artifact.
  2. A separate privileged workflow publishes it: either `workflow_run`, gated on a maintainer label or an environment with required reviewers, or a manual `workflow_dispatch`. It runs `wrangler preview` with **`main`'s** `wrangler.jsonc` on the downloaded `dist/`, and never executes anything from the PR.
  3. GitHub warns that `workflow_run` and `pull_request_target` "may lead to … cache poisoning and granting unintended access to write privileges or secrets" if they run untrusted code.

  The deeper risk: a fork's JS served on our account's domain could phish a user who signs in to the game on that preview. So gate it on human review, and consider Cloudflare Access on fork Previews. (H for the GitHub quotes, M for the design; [GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows), [GitHub secure use](https://docs.github.com/en/actions/reference/security/secure-use))
- **Simplest MVP rule:** previews for same-repo branches only. Fork contributors run `vite dev` (or similar) locally and attach a screenshot. (M)
- **Optional lock-down:** Cloudflare Access can protect "Preview deployments for one Worker" (`preview_worker`) or all Workers' previews. This needs Zero Trust enabled on the account. Reviewers would then need an allowed identity, which works against the outside-contributor goal, so it is not recommended for the MVP. (H, [Workers + Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/), 2026-10-12)

## 6. Secrets handling

- **GitHub:**
  - `CLOUDFLARE_API_TOKEN`: dashboard → Account API tokens → Custom → "Edit Cloudflare Workers", scoped to the one account. Previews need "permission to edit Workers Scripts and the resources used by the Preview". Never commit it. (H, [GitHub Actions for Workers](https://developers.cloudflare.com/workers/ci-cd/external-cicd/github-actions/), [Previews examples](https://developers.cloudflare.com/workers/previews/examples/))
  - `CLOUDFLARE_ACCOUNT_ID`: not sensitive, but keep it as a secret or variable for tidiness.
- **Protect production:** put the deploy job in a GitHub Environment `production` whose deployment branch rule allows only `main` ("Only branches and tags that match your specified name patterns can deploy to the environment"). Optionally store the token as an environment secret ("only available to workflow jobs that reference the environment"). Both are available on public repos. The preview job needs the same token, so a repo-level secret plus the fork guard is the pragmatic MVP setup. (H, [GitHub deployments and environments](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments))
- **Runtime:** the MVP has none. Lava's Firebase web config and OAuth client IDs are already public in every community tool's bundle (ecosystem §1), so they are not secrets. Users' game tokens stay in their own browser and never reach our infrastructure.
- **If a Worker script arrives:** use `wrangler secret put` and `.dev.vars` locally; never use `vars` for sensitive values ([Secrets](https://developers.cloudflare.com/workers/configuration/secrets/), 2026-10-15). Previews take their secrets separately and do not inherit production's ([Previews](https://developers.cloudflare.com/workers/previews/)).

## Open points for later tickets

- **Auth ticket:** confirm that a full Google device-code and Steam `asil` sign-in plus a Firestore `_data/{uid}` read works from our origin. The CORS preflights pass, but Firebase API-key referrer restrictions were not tested.
- **Domain/branding:** pick the domain before users build up browser state on `workers.dev`.
- **Wrangler version:** pin ≥ 4.136.3 in the repo's devDependencies. Previews ignore a newer global install: "project commands do not use a newer global installation" ([Previews](https://developers.cloudflare.com/workers/previews/)).
- **Fork-PR previews:** decide whether to build the gated workflow from §5, or keep fork contributors on local dev plus screenshots.
