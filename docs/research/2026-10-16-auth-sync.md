# Logins and live sync from our own site (2026-10-16)

Ticket: [#5](https://github.com/YassSoliman/idleon-forge/issues/5), part of map [#1](https://github.com/YassSoliman/idleon-forge/issues/1).

Question: can a static web app on our own domain (Cloudflare) sign a player in and receive their **Account State** live, entirely in the browser?

Method: I read the source of IdleOn Toolbox, ha-idleon and AutoReview (pinned commits below), read the game's own web client (`N.js`) for its cloud-save triggers, and ran **harmless live probes** from a made-up origin (`https://activeon-probe.pages.dev`). The probes were CORS preflights, deliberately invalid tokens, and one Google device-code request that nobody completed. **No login happened and no real credentials were used.** Confidence: **H** = read in source, primary docs or a live probe; **M** = inferred from source; **L** = secondhand.

## Answer

- **Yes for Google, email and Steam: a static site on our own Cloudflare domain can sign the player in and stream their save with no backend.** All the endpoints involved answer CORS for any origin, including the game's `asil` cloud function, and Lava's Firebase API key is not restricted to particular sites (live probe, H). Apple is the exception: it needs one tiny proxy we host ourselves.
- **Google (Yasser): device-code flow.** The player opens google.com/device and types a code. The site polls Google every 5 s, swaps the resulting Google id_token for a Firebase session, and then never needs Google again. Nothing to host. This is Toolbox's primary path, and ha-idleon calls it "stable" (H).
- **Steam (Joseph): works, but with one copy-paste.** Steam has to send the player back to `legendsofidleon.com/steamsso/`. The player copies that URL into our site, which posts the OpenID fields to `asil`, gets a Firebase custom token back, and signs in. Nothing to host. Each URL works only once. If the player clicks the big blue button on Lava's page, the URL is used up. We cannot use our own return URL: `asil` is never sent one, so it must rebuild Lava's. ha-idleon tries its own URL, and that path is still "experimental" (M).
- **Email/password: one direct Firebase call.** Nothing to host (H).
- **Apple: we must host a small Cloudflare Worker proxy.** The game's `tspa` and `capsc` functions send no CORS headers (live probe). Toolbox and AutoReview each run their own proxy. We should not rely on Toolbox's proxy (H).
- **Sessions last until the player signs out.** The Firebase JS SDK keeps the session in our origin's browser storage. ID tokens last 1 h and refresh automatically. The refresh token only dies on sign-out, a password or email change, or revocation. So each person signs in once per browser, and Joseph's copy-paste is a one-time step (H, Firebase docs).
- **Live sync works:** `onSnapshot(doc(firestore,'_data',uid))` fires each time the save document changes. Toolbox, our parser source, is built entirely on this (H). Latency is not documented and I could not measure it without logging in. Expect seconds. A live test is needed.
- **What triggers a cloud save** (from the game's own `N.js`, Last-Modified 2026-10-16): an **automatic save about every 4 minutes** of play (not inside dungeons, not on the character-select maps), plus **immediate saves on switching character / returning to character select**, creating a character, the in-game Cloud Save button, gem-shop purchases, and guild GP contributions (H for the code, M for my reading of the minified names).
- **So ActiveOn can be "live" with a lag of up to about 4 minutes,** or instantly if the player switches character or presses Cloud Save. The **Now screen should tell players to cloud-save (or switch character)** whenever they want a fresh **Next Action**.
- **Fallback: Raw Game JSON paste.** Toolbox reads either a bare save or a `{data, charNames, companion, guildData, serverVars, accountCreateTime, tournament}` object from the clipboard and runs it through the same `parseData`. It is cheap to mirror and needs no login, but it is a stale snapshot (H).

## 2. Per-login detail

### Google (Yasser): priority

- **Flow (Toolbox):**
  1. `POST https://oauth2.googleapis.com/device/code` with Lava's Google client ID, scope `email profile`. This returns `user_code`, `device_code`, `expires_in` 1800 and `interval` 5.
  2. The UI shows the code and opens `https://www.google.com/device`.
  3. The site polls `POST https://oauth2.googleapis.com/token` (client ID + **client secret hard-coded in Toolbox**, `grant_type=urn:ietf:params:oauth:grant-type:device_code`) every 5 s. It treats `authorization_pending`/`slow_down` as "keep waiting", and `access_denied`/`expired_token` as errors.
  4. `GoogleAuthProvider.credential(id_token)` → `signInWithCredential`.

  (H) [services/auth/google.js](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/services/auth/google.js), [GoogleLogin.jsx](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/common/Logins/GoogleLogin.jsx), [AppProvider.jsx L523-606](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/common/context/AppProvider.jsx#L523-L606), [firebase/index.js L28-51](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/firebase/index.js#L28-L51)
- **ha-idleon** does the same over REST: device code, then the token, then `accounts:signInWithIdp` with `requestUri=http://localhost`, keeping only the Firebase refresh token (H). [cloud.py L111-155](https://github.com/manix84/ha-idleon/blob/f7ac8a7f247997a239bcd59e6b6135b647724008/custom_components/idleon/idleon_data/cloud.py#L111-L155)
- **Works from another origin:** yes. Both `oauth2.googleapis.com/device/code` and `/token` echo our origin in CORS. A device-code request with Lava's client ID from our origin returned 200 today, so the client is still live and not rotated (H, live probe 2026-10-16; the code was never entered).
- **Host ourselves:** nothing.
- **Note:** Google requires `client_secret` on the device-flow token call, and device-flow clients may only use the `email`/`openid`/`profile` scopes ([Google, updated 2026-10-16](https://developers.google.com/identity/protocols/oauth2/limited-input-device)). That is why every tool ships Lava's secret. It is published in Toolbox's public repo, and we should not copy it into our docs. Lava can rotate it at any time, which would break every tool at once (M).

### Steam (Joseph): priority

- **Flow (Toolbox):**
  1. Open `https://steamcommunity.com/openid/login?...` with `openid.return_to` and `openid.realm` both set to `https://www.legendsofidleon.com/steamsso/`.
  2. The player signs into Steam and lands on Lava's steamsso page. They **copy the address-bar URL** and paste it into the tool. The UI checks that it starts with that prefix and **warns: do not click the big blue button**.
  3. The tool takes `claimed_id` (SteamID), `response_nonce`, `assoc_handle`, `sig` and `signed` and POSTs `{"data":{claimedId,nonce,assocHandle,sig,signed}}` to `https://us-central1-idlemmo.cloudfunctions.net/asil`. This is a Firebase callable function that returns `{result: <custom token>}`.
  4. `signInWithCustomToken`.

  (H) [SteamLogin.jsx](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/common/Logins/SteamLogin.jsx), [services/auth/steam.js](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/services/auth/steam.js), [firebase/index.js L74-84](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/firebase/index.js#L74-L84)
- **Why the blue button matters:** Lava's steamsso page bundle links the button to `/steamandroid/` + the same query string, which hands the one-time OpenID response to the game. A URL that has been used, by that button or a second paste, comes back from `asil` as an empty result, which Toolbox reports as "expired or already used" (H for the link, M for "consumes the nonce"). [steamsso page JS](https://www.legendsofidleon.com/component---src-pages-steamsso-js-acf548e86ed294a2fd3f.js) (Last-Modified 2026-10-16), Toolbox SteamLogin.jsx L57-61.
- **Works from another origin:** yes. The `asil` preflight from our origin returned 204 with ACAO echoing our origin and `allow-headers: content-type`. A POST with garbage fields returned `200 {"result":{}}` with ACAO (H, live probe).
- **Can we use our own return URL to skip the copy-paste? Probably not.** `asil` is sent only `sig`, `signed`, `nonce`, `assocHandle` and `claimedId`, never the return URL. To check the signature with Steam it must therefore rebuild `return_to` itself, which is presumably Lava's steamsso URL (M). ha-idleon sends Steam back to its own Home Assistant callback and calls `asil` with the same five fields. Its README still calls Steam **experimental**, "until validated against more real-world linked accounts" (H). AutoReview, updated 2026-09-23, keeps the copy-paste and states "its OpenID realm is locked to legendsofidleon.com" (H). [ha-idleon cloud.py L593-658](https://github.com/manix84/ha-idleon/blob/f7ac8a7f247997a239bcd59e6b6135b647724008/custom_components/idleon/idleon_data/cloud.py#L593-L658), [steam_auth.py](https://github.com/manix84/ha-idleon/blob/f7ac8a7f247997a239bcd59e6b6135b647724008/custom_components/idleon/steam_auth.py), [AutoReview firebase-auth.js L114-200](https://github.com/TwoSpookyBoos/IdleOnAutoReviewBot/blob/05ac4496c335644dedd68e0be65ac893971efc73/mysite/static/scripts/firebase-auth.js#L114-L200)
- **Idea to make it easier (untested, for the decision ticket):** a bookmarklet the player clicks while on Lava's steamsso page could forward `location.href` to our site (e.g. `https://<ours>/steam#<url>`), turning copy-paste into one click. It only reads the page's own URL. It still has to happen before the blue button.
- **Host ourselves:** nothing.
- **Session:** the custom token is single-use. After `signInWithCustomToken` Joseph has an ordinary Firebase session with a refresh token, so the copy-paste happens **once per browser** (see section 3).

### Email/password

- `signInWithEmailAndPassword(auth, email, password)` in the browser, or `accounts:signInWithPassword` over REST (ha-idleon). Nothing to host. Only works for accounts that actually set a password (H). [firebase/index.js L53-72](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/firebase/index.js#L53-L72), [EmailLogin.jsx](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/common/Logins/EmailLogin.jsx)

### Apple

- **Flow:**
  1. `POST tspa` returns `{device_code, h_nonce, statusToken}`.
  2. Open `https://appleid.apple.com/auth/authorize` with client_id `com.lavaflame.idleon.service.signin`, `redirect_uri=https://us-central1-idlemmo.cloudfunctions.net/xapsi`, `response_mode=form_post`, `code=device_code`, `state=statusToken`. The popup is opened empty on click because Safari blocks `window.open` outside the click.
  3. Poll `POST capsc` with `device_code` + `statusToken` until it returns `{id_token, nonce}`.
  4. `OAuthProvider('apple.com').credential({idToken, rawNonce})` → `signInWithCredential`.

  (H) [services/auth/apple.js](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/services/auth/apple.js)
- **Works from another origin: not directly.** The `tspa` and `capsc` preflights and POSTs from our origin returned no `access-control-*` headers (H, live probe). Toolbox routes both through `appleauth.idleontoolbox.workers.dev/?url=…`. AutoReview runs its own Flask proxy at `/apple-auth/<step>`, with the comment "Lava's tspa/capsc send no CORS headers" (H). [AutoReview flask_app.py L269-277](https://github.com/TwoSpookyBoos/IdleOnAutoReviewBot/blob/05ac4496c335644dedd68e0be65ac893971efc73/mysite/flask_app.py#L269-L277)
- **Host ourselves:** a two-route Cloudflare Worker that forwards POSTs to `tspa`/`capsc` only (allow-list those two URLs, not a generic `?url=` proxy). Toolbox's worker echoes any origin, but it is a third-party dependency we should not build on.
- Neither Yasser nor Joseph needs Apple for the MVP. Recommend deferring it.

Implication: the session belongs to the browser profile on our domain, so the same person on another device signs in again. A server-side poller (ha-idleon style) would need the refresh token stored on a server. That is out of MVP scope per the map.

## 4. Live sync

- **Mechanism (Toolbox):** after sign-in it bootstrap-reads `_uid/{uid}`, `_vars/_vars` and `_TOURNAMENT`, then calls `onSnapshot(doc(firestore,'_data',uid))`. On **every** snapshot it re-reads `_comp`, `_usgu`, `_tournament`, `_T_RES_UID` and `_TOURNAMENT` (and the guild), then runs `parseData`. It deliberately skips a `getDoc` first, because the listener delivers the document anyway, and drops `includeMetadataChanges` so metadata-only events don't re-parse (H). [firebase/index.js L99-182](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/firebase/index.js#L99-L182)
- **Does it fire on every cloud save?** Firestore listeners fire "each time the contents change" ([Firestore listen docs](https://firebase.google.com/docs/firestore/query-data/listen)). Every cloud save rewrites `_data/{uid}` with new timestamps and counters, so in practice every save that changes anything fires (H for the mechanism, M for "every save changes the document"). Toolbox's own active-drop calculator tells users "Cloudsave in-game to update the results", which matches (H). [DropSection.jsx L61](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/tools/active-calculator/DropSection.jsx#L61)
- **Latency: unmeasured.** Firestore makes no numeric promise. Server-to-listener push is normally on the order of a second, but **the real lag is dominated by when the game decides to save** (below). Measure it in the first live test: Yasser presses Cloud Save and times when the Now screen updates.
- **What triggers a cloud save.** Read from the game's web client `https://www.legendsofidleon.com/ytGl5oc/N.js` (26 MB, Last-Modified 2026-10-16 17:09 GMT, so the current patch). The function `_customBlock_CloudSAVE` (which writes save version `CSver` 34.05) is called from:
  - **`_event_Every1sec` (automatic timer):** a counter `CloudSaveCD` goes up by 1 each second, except on maps 20–23 and in the tutorial. When it passes **240** and the player is not in a dungeon, the game cloud-saves and resets the counter. So it saves **about every 4 minutes** during play (H for the code).
  - **`_event_Menutype` (3 call sites):** saves when switching to another character, picking a character, and the character-menu Cloud Save action (M: minified names). Community posts agree: "When you go to character selection, you cloudsave" ([Steam forum, 2023-06-09](https://steamcommunity.com/app/1476970/discussions/3/3836550304879109385/), L, old).
  - `_event_cloudsave`, the Cloud Save menu, polled every 30 s; `_event_CreateNewChar`; `_event_3` (two UI buttons); and a `gemshopCloudsave` flag after a gem-shop purchase (H/M).
  - **Pull the next save forward:** guild GP contribution sets the counter to 250 (saves within about 1 s), and opening certain gift items sets it to 237 (about 4 s). A sailing chest has a 15% chance of an immediate cloud save (H).
- **What this means for ActiveOn:** without the player doing anything, the Account State on our side is at most about 4 minutes old. To refresh it now, the player **switches character or presses Cloud Save**. The UI should show "last cloud save: Xs ago" (Toolbox stores `lastUpdated` per snapshot) and teach that trick.
- **Note on reads:** every snapshot costs about 6 more reads on Lava's Firebase in Toolbox's design. We only need the side reads the parsers require. Being a light client protects everyone's access (M).

## 5. Manual "Raw Game JSON" fallback

- **Import (Toolbox):** `handleLoadJson` runs `JSON.parse(navigator.clipboard.readText())` and accepts either the full object `{data, charNames, companion, guildData, serverVars, accountCreateTime, tournament}` or a bare save (then `data = content`). It calls the same `parseData` and marks the state `manualImport: true`. It is reached from the user menu's "paste data" item (H). [helpers.js L947-982](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/utility/helpers.js#L947-L982), [UserMenu.jsx L142](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/components/common/NavBar/UserMenu.jsx#L142)
- **Where users get the JSON:** in Toolbox, "Copy raw data" (`copyRawData`, save only, with `MapBon` trimmed) or "Copy for support" (`copyForSupport`, the full object plus extra data), and Settings → "Raw game data". So anyone signed into Toolbox can paste into ActiveOn (H). [helpers.js L934-945](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/utility/helpers.js#L934-L945), [settings.jsx L430-449](https://github.com/Morta1/IdleonToolbox/blob/f1e4240a64b8e90ae21acb5dadc778cd66dc0f38/pages/settings.jsx#L430-L449)
- **Value:** no login and no Lava endpoint, so it still works if Lava rotates the OAuth client or adds App Check. It also feeds tests and fixtures. But it is a **static snapshot**, so no live sync. Use the paste field (`clipboard.readText` needs a permission prompt in some browsers) and accept both shapes.

## 6. Risks and things a decision ticket must know

- **Everything rides on Lava's clients and functions** (Google client ID and secret, `asil`, `tspa`/`capsc`/`xapsi`, an API key with no referrer restriction). Any rotation or App Check rollout breaks every tool at once. The JSON paste is the only path that survives that (M).
- **Steam remains a paste-a-URL step.** Verify the bookmarklet idea and the "own return URL" question with Joseph's real login, by Joseph himself, never by an agent.
- **Apple needs a Worker,** so it is not "zero backend". Skip it for the MVP.
- **Live-sync lag is up to about 4 minutes by design of the game,** not of Firestore. Product copy must say so.
- **Possibly outdated:** the Steam forum quote (2023) is old. Everything else was read from code or probed on 2026-10-16.
